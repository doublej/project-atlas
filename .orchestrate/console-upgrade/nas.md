# NAS Caddy, DNS and the hostname registry (workstream 3, decision 2)

Read-only research, 2026-10-01. Nothing on the NAS, the registry or the daemon was changed.
Two `caddy validate`/`adapt` runs read the live config from stdin; no file was written, no reload.
Secrets: none printed. Env var names only; bcrypt hashes redacted.

## TL;DR

- Caddy is **v2.11.1** with `dns.providers.porkbun v0.3.1`. **`auto_https prefer_wildcard` does not
  exist on this binary**: the parser rejects it, and v2.10.0 removed it. Since v2.10 a managed
  wildcard covers matching subdomains **by default**. This instance already does that:
  `atlas.jurrejan.com` and about 100 other single-label sites have no certificate of their own and
  present `CN=*.jurrejan.com`.
- The change is **one new NAS file** with two DNS-01 wildcards. `caddyDev.ts` needs **no change**
  for certificates. The snippet passed `caddy validate` against the full live config.
- The 403 claim is a **real mechanism that is not happening right now.** Hairpinned LAN traffic
  reaches Caddy as the WAN IP (seen in the log). Today's public IP `<home-WAN-IP>` is on the
  `admin_ranges` list, so every `.atlas.local` request returns 200. It breaks the moment Ziggo
  changes the WAN IP.
- **Split-horizon through public DNS cannot work on this LAN.** The Sagemcom (Ziggo) router drops
  every plain-DNS answer that contains an RFC1918 or loopback IP, *in transit, to any resolver*.
  Verified from the Mac, the NAS and Ubuntu. Only DoH gets through. DHCP hands out Google DNS and
  the NAS runs no DNS server.
- Registry: 18 rows, matching the 18 `*-atlas.caddy` NAS files one to one. 4 rows carry
  `~/Documents/development` paths, 0 are unsynced, 0 have a missing path, 0 have a stale slug.
  1 legacy NAS file has no registry row (`multi-stack-framelink-homepage-dev.caddy`).
- Off-LAN console: set `remote: true` on the `atlas` service, then rebuild and reload (the JSON is
  bundled). `CADDY_DEV_AUTH_HASH` is set in the plist and the running daemon. The generated blocks
  have **no `encode`**: the console HTML is 1.42 MB and `/api/projects` is 567 KB, both sent
  uncompressed.

## 2. The wildcard change (decision 2)

### `prefer_wildcard`: do not use it
```
$ docker exec -i caddy-porkbun caddy adapt … < '{ auto_https prefer_wildcard }'
Error: … auto_https must be one of 'off', 'disable_redirects', 'disable_certs', or 'ignore_loaded_certs'
```
The v2.10.0 release notes say: "now wildcards, if present, will be utilized for subdomains, rather
than obtaining individual certificates" and "The experimental `auto_https prefer_wildcard` option
has been removed." Adding it would fail `caddy validate`, and every atlas push would then fail.

### Snippet: new file `sites/atlas-wildcard.caddy`
The name deliberately does **not** end in `-atlas.caddy`. That suffix is caddyDev's slug namespace,
and a doctor that lists `*-atlas.caddy` must not see this file.
```caddy
# atlas dev hostnames: one DNS-01 wildcard per zone instead of two HTTP-01 certs per slug.
# A slug with no route of its own gets a plain 404 with valid TLS (before: handshake failure).
*.atlas.local.jurrejan.com, *.atlas.remote.jurrejan.com {
	tls {
		dns porkbun {
			api_key {env.PORKBUN_API_KEY}
			api_secret_key {env.PORKBUN_API_SECRET}
		}
	}
	respond 404
}
```
- I validated it against the full live config (`import /etc/caddy/Caddyfile` plus this block, sent
  over stdin): `Valid configuration`, exit 0. Only the two pre-existing warnings appear.
- The adapted TLS policy merges both wildcards into the DNS-01 policy with `*.jurrejan.com` and
  `wildeburg.uitgelegd.info`.
- Caddy obtains a separate certificate per name, so this is 2 new certs in total.
- **Use `respond 404`, not `import handle_proxy_errors`.** The adapter adds a wildcard's
  `handle_errors` as an error route matching `*.atlas.local`/`*.atlas.remote`. That route would
  catch errors from every specific atlas block, none of which has its own `handle_errors`: dead dev
  servers' 502s would become styled pages. `respond` adds no error route, so the existing hosts
  behave exactly as before.

### Does caddyDev.ts have to change? No, not for TLS
- Existing and future `<slug>-atlas.caddy` blocks pick up the wildcard automatically, the same way
  `atlas.jurrejan.com` already uses `*.jurrejan.com`. No `tls` line is needed.
- The 35 individual certs stop being managed and expire on their own (2026-11-28 to 2026-12-30).
  Caddy's storage cleaner removes them; nothing to do.
- After the change, a new registration costs zero ACME certs and about 0.5 s of reload.
- Docs that go stale once this is live:
  - root CLAUDE.md "Dev hostnames each cost two ACME certificates…"
  - `~/.claude/skills/atlas-hostname/SKILL.md`: the "Every registration costs two ACME certificates" and "No bulk registration (certificate cost)" lines
  - mechanism.md §9

## 3. "`.atlas.local` from this Mac → WAN IP → 403 when the IP isn't listed"

**Evidence (2026-10-01):**

| Check | Result |
|---|---|
| `scutil --dns` | resolver #1 on en0: `2001:4860:4860::8888/8844`, `8.8.8.8`, `8.8.4.4` (Google). No manual DNS on Wi-Fi |
| DHCP (`ipconfig getpacket en0`) | router `192.168.178.1` (Sagemcom Broadband, from the MAC OUI) hands out `domain_name_server {8.8.8.8, 8.8.4.4}` |
| `dig +short` atlas/web-eink/unregistered/`atlas.jurrejan.com` | `<home-WAN-IP>` from the default resolver, `@8.8.8.8` and `@192.168.178.1` alike. No AAAA. `@192.168.178.100` times out (the NAS runs no DNS) |
| NS for `jurrejan.com` | porkbun |
| Public IP (`api.ipify.org`) | `<home-WAN-IP>`, **on** `admin_ranges` |
| `curl https://atlas.atlas.local.jurrejan.com/api/health` | **200** via `<home-WAN-IP>`, 0.09 to 0.14 s |
| Same with `--resolve …:192.168.178.100` (direct LAN) | **200** |
| `web-eink.atlas.local` / `web-kunstuitleen-gallery.atlas.local` | 502 (no dev server) / 200 |
| Caddy log, source IP of LAN traffic | `"remote_ip":"<home-WAN-IP>"`, i.e. hairpin NAT presents the WAN IP. The `192.168.178.0/24` entry only helps clients that connect to the NAS's LAN IP directly |

**Conclusion: real, but latent.** The `.atlas.local` gate on this LAN depends entirely on the
current WAN IP being in `admin_ranges`. Right now it is, so nothing breaks.

It breaks in three cases:
1. Ziggo reassigns the WAN IP. The homenetwork doc names `<other-allowlisted-IP>` as the home WAN while DNS
   says `<home-WAN-IP>`, so the IP has probably moved once already.
2. The Mac egresses elsewhere: off-LAN or on a non-home VPN. A 403 there is intended.
3. An AAAA record is added: LAN clients would then arrive with their global v6 address, which is
   not on the list.

A WAN change also makes the `*.jurrejan.com` A record stale. No DDNS updater exists anywhere in
the homenetwork repo, so the whole of `*.jurrejan.com` breaks with it, not just atlas.

**Split-horizon: where it could go**
- **A public record `*.atlas.local.jurrejan.com A 192.168.178.100` is dead on arrival.** The
  Sagemcom drops plain-DNS responses that carry private or loopback IPs, in transit, to any
  resolver. `192.168.178.100.sslip.io`, `10.0.0.1.sslip.io` and `localtest.me` all time out
  `@8.8.8.8` (UDP and TCP, v4 and v6), `@1.1.1.1` and `@192.168.178.1`. The same happens from the
  NAS (`nslookup … 8.8.8.8`) and Ubuntu. `1.2.3.4.sslip.io` resolves fine, and DoH
  (`dns.google/resolve`) returns the private answer. This confirms the `caddyDev.ts` comment.
  (macOS's own resolver did return the private IP, probably over an encrypted path; other LAN
  devices cannot count on that.)
- **A LAN DNS server** (dnsmasq/AdGuard Home on the NAS or Ubuntu, answering
  `*.atlas.local.jurrejan.com → 192.168.178.100` and forwarding the rest) works, because the answer
  never crosses the router. It needs two things:
  1. The Sagemcom's DHCP DNS field pointed at it. The field exists: it is set to Google today.
  2. A DHCP reservation for that host. None exist, and the M2 has already drifted.

  The blast radius is all LAN DNS. That is a household decision, not an atlas one.
- **Per-Mac only:** `/etc/resolver/atlas.local.jurrejan.com` pointing at such a server. This Mac
  gains, phones don't.
- **Recommendation:** no DNS change now. The hostname doctor detects the failure instead: compare
  `api.ipify.org` with `admin_ranges` (read over `ssh nas`) and with `dig +short x.jurrejan.com`,
  and print "WAN IP changed — update admin_ranges in snippets/common.caddy and the porkbun `*` A
  record". The real fix is a DDNS job that updates both. It belongs to homenetwork, not atlas.

## 5. Off-LAN console (decision 1)

- **Enable:** `shared/services.json` → `{ "slug": "atlas", …, "remote": true }`.
  - `shared/services.ts` imports the JSON statically, so the change needs `bun run build` plus
    `bun run daemon:reload` (JJ/orchestrator).
  - The next 60 s sync sees `remote` changed (`isCurrent` false) and pushes a block with
    `atlas.atlas.remote.jurrejan.com { basic_auth { dev <hash> } reverse_proxy 192.168.178.180:47891 … }`.
  - The daemon binds `127.0.0.1` (plist `HOST`), so the request goes through the services.ts NAS-only
    bridge, as `.atlas.local` does today. No change there.
- **Auth hash:** `CADDY_DEV_AUTH_HASH` is **present** in `atlas-api/launchd/com.jurrejan.atlas-api.plist`
  and in the running daemon's environment (`launchctl print`: 1 line; value not printed).
  - bcrypt cost 14. `CADDY_DEV_AUTH_USER` is unset, so the user is `dev`.
  - If the hash were missing, `renderSiteBlock` would drop the remote block silently, while
    `ensureRoute` still returned a `remote` URL. Doctor check: "remote expected, NAS file has no
    `atlas.remote` block".
- **Order:** apply the wildcard first, and `atlas.atlas.remote` costs no cert. Before it, the remote
  block costs one HTTP-01 cert.
- **Read-only must live in atlas-api, not Caddy.**
  - Reads also use POST (`/api/git`, `/api/readme`), so a Caddy method filter would break them.
  - Smallest guard: a `handle` in `src/hooks.server.ts` (it has only `init` today). When
    `x-forwarded-host` ends in `.atlas.remote.jurrejan.com`, refuse anything other than GET/HEAD
    and the read-POSTs with 403.
  - That header is trustworthy: Caddy sets it from the real Host, because clients are not in
    `trusted_proxies` (only the 127.0.0.1 layer4 hop, which PROXY protocol rewrites to the real
    client).
  - `/api/disk` writes already refuse `atlas.remote` (`requireLocalRequest`, `disk.test.ts:103`).
- **Compression: none today.**
  - The generated blocks carry no `encode`. Through the NAS:
    - `/` returns 1,420,981 B of `text/html` with no `content-encoding`.
    - `/api/projects` returns 566,932 B of `application/json` with no `content-encoding`.
    - `/_app/immutable/*` already comes back `br`, from adapter-node's default precompress.
  - Estimated sizes once compressed:
    - HTML: 134,845 B with gzip -6, 112,965 B with zstd -3 (about 10×).
    - JSON: 77,802 B with gzip (about 7×).
  - Needed:
    1. Add `\tencode zstd gzip` as the first line of **both** blocks in `renderSiteBlock`, the same
       line `sites/agenda.caddy` already uses. Encode skips the `br` assets and leaves websocket
       upgrades (HMR) alone.
    2. Add a re-push trigger. `isCurrent` compares port/ip/devPublic/remote/host/nasSynced and
       never the block text, so a template change never reaches the 18 existing files. Store a
       `rev` constant in the entry and compare it in `isCurrent` (or let the doctor's resync
